# 12 — Technical direction: what to build, what to stop building

This document decides between three strategies using evidence from this
repository and this host. It is written to be argued with: every claim names
what would falsify it.

- **A. General-purpose compatibility frontend** — engines, bottles, installers,
  Finder integration, compatibility data.
- **B. Independent binary-nativeization engine** — translate Windows x86-64 into
  optimized ARM64 and execute it natively.
- **C. Performance optimization layer** — verified, application-specific
  optimizations that work alongside an existing compatibility runtime.

The brief prefers B+C. The audit in `docs/11-competitive-analysis.md` and the
measurements in `docs/13-nativeization-experiment.md` say that B+C, as usually
imagined, cannot work on macOS today. This document explains exactly which part
is blocked, which part is merely hard, and what is left.

---

## 1. The constraint that decides everything

A native ARM64 optimizer for Windows programs assumes it can put ARM64 code into
the process that runs the Windows program. On macOS that process is an x86-64
Mach-O under Rosetta. It cannot host ARM64 code. Measured here:

```
$ clang -dynamiclib -arch arm64 -o libnative.dylib native.c
$ clang -arch x86_64 -o loader loader.c
$ arch -x86_64 ./loader
dlopen failed: ... (mach-o file, but is an incompatible architecture
(have 'arm64', need 'x86_64'))
```

This is not a permission Porte could ask for. There is no mixed-architecture
process on macOS: Rosetta translates a whole process, and its code pages are
generated by Rosetta, not by us. Three consequences:

1. Porte cannot replace a hot function inside Wine with ARM64 code.
2. Porte cannot inject an ARM64 dylib, JIT region, or trampoline into a Wine
   process.
3. Porte cannot even *name* the guest's hot code: the sampler reports `Rosetta
   JIT` addresses, not originating instruction addresses, and Wine's Win32
   modules are translated the same way. The measurement in `docs/13` shows this
   directly (28,739 samples; the split between `7z.exe` and Wine's PE modules is
   not recoverable).

So the "optimization layer next to Wine" must operate in **x86-64 space** (rewrite
the PE and let Rosetta translate the result) or not at all. Rewriting a
third-party x86-64 binary well enough to beat Rosetta's translator is a research
programme with no evidence of payoff: Rosetta's output is already a good ARM64
translation, and the measurable overhead is inside Rosetta's runtime helpers,
which no PE rewrite can remove.

## 2. Strategy A — frontend

| | |
| --- | --- |
| Differentiation | none. Highball implements the same shape with a larger CC0 database, renderer selection and launcher integration (`docs/11` §1). |
| Feasibility | high — already built here |
| Performance potential | none (it is a launcher) |
| Complexity | low, but perpetual (engine drift, store sign-in changes, anti-cheat lists) |
| Licensing | clean |
| Long-term value | low: the layer is commoditised and the maintenance is someone else's race |

Verdict: **stop expanding.** Keep what exists because it works and users need it,
but it is not the product.

---

## 3. Strategy B — independent nativeization engine

What exists: a Unicorn-based x86-64 machine with 15 Win32 stubs, a profiler that
finds a hot reducible loop, a lifter to ARM64 machine code, a differential
oracle, and a persistent cache (`docs/90-opaque-pe-experiment.md`).

| | |
| --- | --- |
| Differentiation | genuine: nobody audited does guarded, profile-driven specialization of an opaque Windows binary with differential proof |
| Feasibility | **low** for real applications |
| Performance potential | measured in `docs/13` §4: 1.3×–37× behind native ARM64, depending on the loop |
| Complexity | very high: to run an unmodified application it must implement enough of `user32`, `gdi32`, `comctl32`, `ole32`, `shell32`, `comdlg32`, `advapi32`, `msvcrt`, SEH, TLS, thread scheduling and the window server bridge — Wine's PE modules, which are decades of work, against 15 stubs today |
| Maintenance | highest of the three |
| Licensing | clean (all original) |
| Long-term value | high *if* the API gap could be closed, which it cannot be inside one project's budget |

Verdict: **keep as research, do not present as a product path.** The engine is
the only original asset; it is also three orders of magnitude from running a real
program.

---

## 4. Strategy C — optimization layer beside a runtime

Three variants, not one:

| variant | mechanism | status |
| --- | --- | --- |
| C1: native code injection at run time | replace hot functions with ARM64 inside the Wine process | **impossible** — §1 |
| C2: ahead-of-time x86-64 PE rewriting | rewrite the guest binary, keep it x86-64, let Rosetta translate the better code | possible in principle; no profiling feedback inside Rosetta; would compete with Rosetta's translator on its strongest ground; no measured evidence of a win |
| C3: API-boundary reduction | fewer Win32 calls, less cross-domain work (graphics, registry, file I/O) via shims/prefix configuration | possible; measurable; but it is what DXMT/DXVK/Wine already do, and gains are workload-specific |

| | |
| --- | --- |
| Differentiation | C1 none (impossible); C2 research; C3 weak (occupied) |
| Feasibility | C1 no; C2 unknown; C3 medium |
| Performance potential | C1 would be large (≈half of executing samples are Rosetta runtime), C2 unknown and likely small, C3 small |
| Complexity | C2 high; C3 medium |
| Licensing | clean |

Verdict: **C1 is dead, C2 is a research question without a feedback signal, C3 is
a maintenance treadmill.**

## 6. What would have to be true for B to win

B becomes viable only if one of these becomes true. Each is a falsifiable
condition, not a hope:

1. **A native ARM64 Wine exists on macOS.** Then the EU/PE side can be ARM64,
   Rosetta is out of the picture, and an optimizer could emit ARM64 modules into
   a native process. Status today: Wine's macOS builds are x86-64; Wine's
   ARM64EC support targets Windows on ARM. Not available.
2. **Porte implements the Win32 surface for a *narrow* class of programs** (for
   example console tools that use only `kernel32` file/console calls). Then the
   engine is genuinely usable for that class, and nativeization has something to
   accelerate. This is the only version of B that fits in one project.
3. **A measurement shows PE-level rewriting beats Rosetta by a reproducible
   margin.** No such measurement exists, and the profile in `docs/13` suggests
   the removable overhead sits in Rosetta's runtime, not in the guest's
   instruction stream.

Condition 2 is the only one Porte can act on now. It is a real, bounded product:
"run Windows console tools natively on Apple silicon, faster than Wine, with
proof of equivalence" — for tools whose imports Porte serves.

---

## 7. Recommendation

1. **Stop building frontend features.** The GUI, bundles, Finder integration and
   MSI path stay as they are; they are support, not the product.
2. **Do not claim B or C as a plan.** Present the engine as research with the
   numbers from `docs/13`, including the ceiling.
3. **Pick the narrow B**: make the engine run a *class* of real Windows programs
   (console tools with a small import surface), then measure against Wine on the
   same workload. This is the only path where Porte's differentiation
   (specialization + oracle) touches software a user actually has.
4. **Integrate rather than duplicate** for everything compatibility-related:
   Highball's CC0 recipes/database are licence-clean to consume; Wine/DXMT fixes
   belong upstream. Contributing there earns credibility that a second launcher
   cannot.

If step 3 fails its go/no-go gate, the correct outcome is to stop claiming an
execution platform and either contribute upstream or archive the engine.

---

## 8. Go / no-go criteria for the next milestone

The next milestone is **"native execution of a real, unmodified Windows console
program"**, not a GUI program. It is a go only if all of these hold:

| # | criterion | measurement | bar |
| --- | --- | --- | --- |
| 1 | A real third-party Windows console program runs to completion in the engine | exit code and stdout compared with Wine on the same input | byte-identical over ≥ 20 cases, 0 crashes |
| 2 | Only documented host APIs are stubbed | import inventory of the program vs `api_*` coverage | 100% of imports served, no silent fallback |
| 3 | Speed against Wine on this host | same workload, 7 repeats, median | ≥ 1.0× (parity) to justify existing |
| 4 | Correctness under adversarial inputs | boundary corpus (0, 1, sizes ±1, large) | no divergence |
| 5 | Maintenance cost is bounded | lines of new host code per supported DLL | ≤ 500 lines per DLL family |

No-go if criterion 3 lands below parity after the engine is *complete* for that
program class: at that point Wine + Rosetta is simply better, and Porte should
not ask anyone to use it.

The current state against these criteria is in `docs/13-nativeization-experiment.md`
§5: criterion 1 is **not met** (no real console program runs yet), criterion 2 is
15 stubs, criterion 3 is undefined for real programs, criterion 4 holds only for
the fixtures, criterion 5 is untested.
